# Assumption Ledger

The goal of this ledger is to prevent implicit assumptions from entering the
review package.  Every remaining nontrivial premise must be classified here.
The detailed review with risk analysis and closure criteria is
[assumption_review.md](assumption_review.md).

## Proved In Lean

- q14 reconstructed-commitment byte encoder round-trips through the q12289
  decoder.
- The frozen 17-byte production challenge layout has a computable Lean codec
  with `decode(encode(c)) = c`, injectivity, and slack-bit rejection.
- The q12289 hash frame is fixed as a concrete byte string with proven length
  `1508 + messageLen`.
- Accepted serialized transcripts imply the product-block verifier equation,
  conditional on `ProductionHashFrameOracleAgreement`.
- The chosen q12289 `3 x 2` local block has an internal Lee certificate for
  the current proof boundary.
- The generated profile records the current public key and signature sizes.

## Cryptographic Assumptions

`A1: ProductionHashFrameOracleAgreement`

- Meaning: SHA-256-to-challenge over the exact `q12289HashFrame` agrees with
  the query-log/random-oracle challenge on accepted transcripts.
- Status: accepted as the Fiat-Shamir random-oracle assumption for review.
- Review risk: the theorem proves a random-oracle-model statement, not a
  standard-model theorem about SHA-256.

`A2: Query-log Fiat-Shamir game correspondence`

- Meaning: the deployed EUF-CMA game maps to the finite query-log model, so a
  forgery either queried the exact challenge point or is charged to the
  `2^-133` blind challenge event.
- Status: formal query-miss machinery exists and `target_theorem.md` states the
  intended EUF-CMA-style ROM claim; the exact game-event-to-Lean dependency map
  is still open.
- Review risk: a game mismatch can make the theorem too narrow for the
  deployed claim.

`A3: Canonical challenge byte-codec conformance`

- Meaning: the production 17-byte little-endian challenge layout denotes the
  same `N32CanonicalChallenge` object used by Lean.
- Status: closed for the frozen layout by
  `N32CanonicalChallengeByteCodec.productionBitLayout17`,
  `productionDecode_encode`, `productionEncode_injective`, and the generated
  `q12289_conformance_vectors.json` bundle.
- Review risk: future format drift would invalidate the deployed verifier claim
  unless the codec proof and vectors are regenerated.

`A4: Structured q12289 keygen/no-bad-vector assumption`

- Meaning: the public view generated by keygen does not admit the relevant
  short/narrow public-view witness that would invalidate the extraction claim.
- Status: partially supported by internal Lee certificates and search
  artifacts, but must be attacked explicitly before review.
- Review risk: this is the largest mathematical risk if the scheme is to be
  treated as deployable cryptography.

`A9: Frozen-target concrete cryptanalysis`

- Meaning: the target security level is supported by failed attack reports
  against the exact q12289 candidate, not only by the formal blind-guess term.
- Status: plan exists; report is not complete.
- Review risk: a practical attack on keygen, transcript structure, or signing
  leakage would bypass the narrow theorem boundary.

## Implementation Assumptions

`A5/A7: Reference implementation conformance`

- The implementation must use the exact byte encodings in `target_spec.md`.
- The implementation must reject every noncanonical encoding listed there.
- The implementation must compute the same `q12289HashFrame` as Lean.
- The no-structural-failure theorem is a deployment fact only after these
  checks are enforced by the verifier and covered by negative vectors.

`A6: Concrete signer distribution`

- The concrete rejection sampler must instantiate the abstract
  `RejectionSamplingCertificate`.
- Accepted serialized signatures must be secret-independent apart from public
  data.
- Retry behavior must be hidden or modeled.

`A8: Secret handling`

- Signing and keygen must avoid secret-dependent timing or memory access where
  practical.
- Randomness generation must be reviewed and testable.

## Not Yet Claimed

- No standard-model proof for SHA-256.
- No side-channel security proof.
- No third-party cryptanalysis.
- No performance-optimized implementation.
- No compatibility promise for any future parameter or byte-format change.

## Assumption Exit Criteria

Before third-party review, each assumption must have:

- precise statement;
- exact Lean endpoint or document reference;
- known attack surface;
- evidence or rationale;
- owner/status;
- reason it is acceptable for the target claim.
