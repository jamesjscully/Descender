# KAT — Known-Answer Test Corpus (cross-tool conformance anchor)

> MIGRATION STATUS (2026-06-20): `LEGACY_FORMAL`.
> KAT v0 remains a frozen byte-conformance corpus for the legacy linear-sigma
> baseline. It is not the current product authorization format and is not a
> soundness claim. Future active-path KATs should be introduced as new versioned
> corpora rather than mutating this historical one. Current product authority
> starts at `../../spec/README.md`.

**Owns:** byte-for-byte agreement across every implementation (Rust reference,
Jasmin core, any Lean/hax executable model). This is the *one* machine-checkable
artifact that ties the tools together where proofs cannot span them (seams 1/3).

**Status:** KAT v0 delivered — see [`kat_v0.json`](kat_v0.json) (frozen corpus)
and [`kat_v0.md`](kat_v0.md) (human-readable index). 3 positive + 8 negative
vectors (7 distinct reject reasons), generated from the real Rust reference
pipeline (`production_keygen`/`production_sign`/`production_verify` in
`tools/parameter-search/src/bin/signature_q12289_local_delta_stateful.rs`).

Regenerate / check:

```
cd tools/parameter-search
cargo run --bin signature_q12289_local_delta_stateful -- --kat-generate   # freeze
cargo run --bin signature_q12289_local_delta_stateful -- --kat-check      # CI gate
```

CI runs `--kat-check` (and the `kat_v0_corpus_reproduces_frozen_json` test) so
any byte-level drift fails the build.

**First deliverable (KAT v0):** freeze a reference corpus generated from the Rust
reference:
- positive: keygen → sign → verify round-trips for fixed seeds/messages/slots;
- negative: non-canonical encodings, mutated challenge/response/carrier, replayed
  slot, stale account root, public-representative forgery probe;
- each entry: inputs (hex) + expected output (accept/reject + reason + byte
  outputs), with the producing-version digest pinned.

Every implementation that claims KAT v0 conformance must reproduce it exactly;
CI still runs it for the legacy baseline. Future active-path corpora should get
new KAT versions so the historical byte anchor remains reproducible.

## Active Path Draft Boundary Manifest

`path2_account_stark_payload_kat_boundary_v1.json` is a draft active-path
boundary manifest generated by:

```
cargo run --manifest-path tools/parameter-search/Cargo.toml --bin path2_account_stark_payload_kat_manifest
```

It pins the current `Path2AccountStarkCreationPayloadV1` mutation-case ids,
public rejection-class mapping, and report digests. It is not a frozen vector
corpus and does not supersede KAT v0. The build gate regenerates the JSON and
diffs it byte-for-byte so drift is explicit while the full active Path 2 corpus
remains open.

`path2_account_stark_payload_kat_vectors_v1.json` is the active-path
digest-pinned boundary vector corpus generated by:

```
cargo run --manifest-path tools/parameter-search/Cargo.toml --features account-creation-stark-verifier --bin path2_account_stark_payload_kat_vectors
```

It runs the real account-creation STARK fixture, verifies the honest payload,
executes every current boundary rejection row, and pins stable public fields,
deterministic payload-frame/account-STARK bundle digests, payload/bundle lengths,
mutation recipes, observed errors, and public rejection classes. The generator
uses the explicit seeded KAT producer inside a single-thread Rayon pool so
Plonky3 proof-of-work witness selection is reproducible; the deployment producer
still uses fresh proof randomness.
