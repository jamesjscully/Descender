## Direct Mode: First Deployable Target

### Deployment Sequencing (Economically-Viable Quantum-128 Standard)

Goal: bring Descender to an economically-viable, quantum-128, deployable security
stack for a PQ Ethereum blockchain — everything except external third-party
cryptanalysis (the one irreducibly-external gate, `DIR-REVIEW-001`). `ADR-0008`
fixes the quantum-128 bar. Priority order, each step gating the next:

1. **Quantum-128 committed** — `ADR-0008` / `ADOPT-128-001` (decision recorded).
2. **Re-parameterize the account-STARK to quantum-128** — `DIR-QROM-001` / `DIR-STARK-001`: ~120 FRI
   queries + Poseidon2 capacity `c=9` + KAT/byte-model refresh + re-priced
   FRI-AoK/QROM/binding, then re-cost proof size/gas. Sizes everything downstream.
3. **Mode B aggregation for economic viability** — `AGG-ROLLUP-001`: per-tx on-chain
   STARK verification is too costly (worse at q128 proof sizes), so block-level/rollup
   aggregation moves onto the deployable critical path — the chain verifies one
   aggregate, not N proofs.
4. **Close F2, the reorg-safe pad-seed seam** — `DIR-LIFE-001` / `ADOPT-HW-STATE-001`:
   a global cross-account pad-seed registry at admission plus the ADR-0010 D2
   finalized-head reorg policy; D2 selection and execution are now digest-pinned
   in the lifecycle boundary, with local lifecycle transition vectors, the D2
   safe-default lifecycle profile review, and the D2 lifecycle profile
   verification now digest-pinned while broader deployment-profile readiness
   remains open.
5. **Freeze the KAT corpus + deterministic consensus-safe rejection** — `DIR-STARK-001`
   / `DIR-REJECT-001` / `DIR-KAT-001`: byte-reproducible vectors for every rejection
   class (parser ambiguity or nondeterministic rejection = a consensus split on Ethereum).
6. **Mechanize the soundness chain / close GAP-B/D** — `DIR-SEC-001` / `DIR-PROOF-001`:
   connect the unlinked EC files under a shared import and mechanize end-to-end.
7. **First deployment profile: ERC-4337 + rollup** — `ADOPT-ETH-AA-001` /
   `ADOPT-ETH-ROLLUP-001` / `ADOPT-HW-CT-001`: lead with the no-hard-fork path before
   precompile/EIP-7702 L1 integration.
8. **External third-party cryptanalysis** — `DIR-REVIEW-001`: excluded from the
   internal goal; the load-bearing external gate (custom coded-SIS core, Poseidon2/
   KoalaBear instance, full composition); production stays fail-closed until complete.

Economic costing (SEQ-2 re-cost, measured 2026-06-27): the account-creation STARK
bundle is **~4.75 MB** at 56 queries (`account_stark_bundle_len = 4748253` in
`formal/kat/path2_account_stark_payload_kat_vectors_v1.json`) — ~76M gas in
Ethereum calldata alone, >2.5x the ~30M block limit, ~36 blobs, and ~9.5 MB at
the quantum-128 query count. Per-account on-chain verification of the creation
proof is therefore categorically non-viable; the creation proof must be verified
off the on-chain hot path (a prevalidator / rollup prover, or Mode B recursive
aggregation), with only the small prevalidated slot-leaf record posted on chain —
which is the intended purpose of prevalidated slots. The compact spend
(~262-318 bytes) is the on-chain hot path and is size-viable; its verification
gas (Poseidon2 FS + separated Fq12 action in the EVM) still needs measurement.
Consequence for the roadmap: economic viability is gated on the off-chain/Mode B
creation-verification path (`AGG-ROLLUP-001`, step 3), so the quantum-128 query
bump should be applied where the proof is actually verified (the prover/recursion
layer), not treated as an on-chain per-tx cost; a raw per-tx query bump only
doubles an already-off-chain proof.
