# Conformance And KAT Corpus

Status: ACTIVE_NORMATIVE

This file defines the active conformance and known-answer-test corpus model for
Descender's chain-native Path 2 authorization stack.

Legacy KAT v0 under `formal/kat/` remains frozen byte-conformance history for
the old linear-sigma lineage. It is not evidence for the active direct-mode
prevalidated-slot product target.

## Scope

The active conformance corpus covers:

- canonical public byte objects and domain constants;
- account/slot admission vectors;
- checked-core spend authorization vectors;
- lifecycle state-transition vectors;
- deterministic public rejection classes;
- signer/wallet/HSM public API vectors for the command/result model in
  `spec/signer_api.md`;
- entropy and domain-separation vectors for the stream model in
  `spec/entropy_profile.md`;
- policy vectors for M-of-N, recovery, rotation, burn, and adaptor-style state
  conditions;
- deployment-profile vectors for target chains, Ethereum surfaces, rollups,
  bridges, and light clients when those surfaces are in scope.

The corpus is conformance evidence, not a proof of cryptographic security. It
shows that implementations agree on bytes, public results, and state transitions
for the stated profile.

## Corpus Identity

Each active corpus version must define:

| Field | Requirement |
|---|---|
| `corpus_id` | stable identifier such as `Descender.Path2.ModeA.KAT.v1` |
| `corpus_version` | monotonic integer or date-stamped version |
| `profile_id` | deployment or generic direct-mode profile used by the vectors |
| `authority_snapshot` | spec, ADR, tracker, and implementation revisions used to generate the corpus |
| `generator` | command and source path that generated the corpus |
| `manifest_digest` | hash over vector files and metadata |
| `result_schema` | accepted public result and rejection-class schema |
| `frozen_status` | `draft`, `candidate`, `frozen`, or `superseded` |

No implementation may claim conformance to a corpus without naming the exact
`corpus_id`, `corpus_version`, and `manifest_digest`.

## Vector Classes

The direct Mode A corpus must include these vector classes before it can support
deployment readiness.

| Class | Required vectors |
|---|---|
| public object canonicalization | domain, version, length, byte order, reserved field, and digest vectors for each public object |
| admission positive | valid account creation evidence admitting one live slot |
| admission negative | wrong leaf digest, wrong evidence field, wrong account, wrong state root, stale version, malformed proof, and duplicate admission |
| spend positive | valid checked-core spend consuming one live slot |
| spend negative | wrong message, wrong account, wrong state root, wrong slot id, wrong lifecycle anchor, wrong proof commitment, and checked-core mutation |
| lifecycle | admit, spend, replay, burn, recovery, rollback, restore, and recoverable-state cases |
| rejection | every public rejection class in `spec/consensus_verifier.md` |
| signer public API | public slot records, fixed public errors, deterministic test-mode outputs, and diagnostic-build exclusion checks |
| entropy streams | stream-domain KATs, deterministic test-mode vectors, wrong-profile/domain mutation vectors, and mask-PRF drift checks |
| policy | M-of-N duplicate prevention, threshold/weight denial, recovery/rotation, timelock, burn, and adaptor-style condition vectors |
| deployment profile | chain/application domain, gas/resource limit, state storage, data availability, and profile-version mismatch cases |

Mode B corpora must add batch ordering, duplicate-slot/signature/account/message
rejection, aggregate statement bytes, recursion or accumulator public inputs,
data-availability handles, committee weights, and light-client proof semantics.

## Result Schema

Every vector must state:

- vector id;
- corpus id and version;
- profile id;
- input object names and hex encodings;
- expected public result class;
- expected state transition or explicit no-state-mutation result;
- expected output bytes, digests, or public handles;
- expected rejection class for negative vectors;
- fields intentionally mutated, if any;
- generator command;
- source authority references.

Negative vectors must mutate one semantic field at a time when possible. If a
single mutation necessarily changes multiple derived fields, the vector must
state the dependency.

Public rejection classes must match `spec/consensus_verifier.md`. Internal error
strings, private witness data, callback diagnostics, retry counts, and
secret-bearing logs must not appear in conformance outputs.

## Reproducibility Rules

The active corpus must be generated by deterministic commands. A conformance
check must be able to:

1. regenerate vector files from pinned inputs;
2. verify the manifest digest;
3. run the reference implementation against every vector;
4. run at least one independent or alternate implementation path when available;
5. fail on byte drift, result-class drift, state-transition drift, or missing
   vector classes.

Generated corpora must not be hand-edited. Corrections require regenerating the
corpus, updating the manifest, and recording the tracker or ADR reason for the
change.

## Versioning And Supersession

KAT corpora are append-only after freeze:

- `draft` corpora may change without compatibility guarantees;
- `candidate` corpora may change only with tracker notes;
- `frozen` corpora must remain byte-for-byte reproducible;
- `superseded` corpora remain available as historical conformance anchors until
  no active support or review package imports them.

A new corpus version is required when public bytes, public result classes,
state-transition semantics, deployment profile identity, or security-relevant
domain constants change.

`DIR-EVID-001`, `DIR-SPEND-001`, `DIR-CC-001`, `DIR-LIFE-001`,

`ADOPT-HW-API-001`, `ADOPT-HW-ENT-001`, and `ADOPT-ETH-AA-001`.

Before the active conformance corpus can be marked `verified`, the repo needs:

- active Path 2 corpus manifest and generator command;
- byte-for-byte positive vectors for direct admission and spend;
- negative vectors for every public field mutation in consensus-visible objects;
- lifecycle vectors for replay, burn, recovery, rollback, and restore cases;
- public rejection-class vectors covering every class in
  `spec/consensus_verifier.md`;
- deployment-profile vectors for any target-chain or Ethereum claim;
- entropy stream vectors, deterministic-test separation vectors, and mask-PRF
  drift checks;
- policy vectors before any multisig, recovery, threshold, committee, or
  adaptor-style claim;
- manifest verification wired into the local and CI build gate;
- explicit separation from legacy KAT v0 evidence.

Until those artifacts exist, `DIR-KAT-001` remains below `verified` and direct
adoption gates 3 and 4 remain below `ready`.
